# Phase 0 and the build plan

## Phase 0: how it actually runs

There's no service. It's one agent session in a harness (for example Claude Code) plus this repo.

| Piece | In phase 0 |
| --- | --- |
| Chief of Staff | The main session; loads `AGENTS.md` (via `CLAUDE.md` in Claude Code) |
| Worker, Reviewer, Operator | Subagents generated by `pmos render claude-code`, each with its own tier and tool list |
| Workflow manager | `scripts/pmos.py`, run through the agents' shell tool |
| State | Files: `state/tasks/*.json`, `traces/*.jsonl`, `outputs/<task>/` |

### What `pmos` is

The deterministic core: one Python script, no model. It is the only writer of task state; it
validates every envelope, result, mode, role and pack against `contracts/`; it runs the registry
(install, admission, grants, exports); it publishes the catalog, `AGENTS.md` and the status board;
it logs every transition; and it generates harness config. Agents think and write; `pmos` keeps
things exact, so a confused agent can stall a task but can't corrupt state.

### How the CoS knows when to call `pmos`

Its manual maps each step of its loop to a command:

| When… | The CoS runs… |
| --- | --- |
| You ask for new work | `pmos catalog --pack <pack>` if needed, then `pmos task new …` |
| You ask what's happening | reads `state/status.md`, or `pmos task show <id>` |
| A delegated agent finishes | `pmos task show <id>`, then delegates review |
| You approve | `pmos task approve <id> --by <you>`, then delegates to the Operator |
| You answer a gate or ask for changes | `pmos task move <id> queued` (or `revise`) with your words |
| You make a decision | `pmos decide "…"` |

It never tracks ids or states from memory; it asks `pmos`. If it gets a step wrong, `pmos`
refuses (illegal transition, wrong inputs, internal mode, approving the wrong state).

### One request, mechanically

1. You type in the session. The CoS reads the catalog and picks the mode by reasoning over mode
   summaries and `accepts`.
2. It runs `pmos task new …`; `pmos` validates and returns an id.
3. It invokes the `worker` subagent with "Work task T-131". Fresh context; the Worker runs
   `pmos task show`, reads systems of record with read-only tools, writes `outputs/`, and submits
   through `pmos task result`.
4. The CoS invokes the `reviewer` subagent the same way.
5. You reply "yes"; the CoS runs `pmos task approve` and invokes the `operator` subagent.

### Phase 0 limits

- **Your thread may wait** if the harness runs subagents in the foreground; with background
  subagents it stays free.
- **Nothing runs unless the session is active**: no daily tracker or Monday check-in unless the
  harness has scheduled tasks.
- **No pushed events**: the CoS learns a run finished when the subagent returns. A new session
  catches up from `state/status.md`, because all state is in files.
- **Routing is the CoS's judgment** over mode summaries; `pmos` refuses bad choices but can't pick
  the right one. A hook that runs `pmos board` when a subagent finishes keeps the board fresh.

## Build plan

| Phase | What | Exit when |
| --- | --- | --- |
| 0 — skills in a harness | Packs, modes and roles as skills; `pmos` for state; subagents for the four agents | A request from your phone becomes a tracked task and a digest comes back |
| 1 — harden contracts | Every mode returns schema-valid JSON; golden tasks per mode; `pmos eval` with a headless runner | First-pass review rate and your edit rate are being measured |
| 2 — codify ladder | Promote `[candidate-code]` steps to scripts: JQL building, field mapping, velocity, dedupe, diffs | High-volume steps run as code; review failures on them drop |
| 3 — durable runtime | CoS as an SDK service; DBOS for workflows, waits and schedules; events pushed to the CoS | Your thread never waits; approvals can wait days; the sprint tracker runs unattended |

### The codify ladder

Every step in a mode's `SKILL.md` is tagged:

- `[model]` — judgment: prioritizing, writing, reviewing. Stays with the model.
- `[candidate-code]` — the model does it today, but it's rule-shaped.
- `[code: script]` — already a script; agents run it instead of reasoning about it.

Promote a step when you can write a unit test for it, or when traces show it's high-volume or keeps
failing review. Codified so far: `check_prd.py`, `capacity.py`, `dedupe.py`, `group_tickets.py`, and
`forge.py` for building packs.

### Rule that keeps phase 3 cheap

Write skills portably from day one: plain skill format, JSON in and out, no harness-specific tricks
inside steps. Then moving to a durable runtime is a runtime swap, not a rewrite.
